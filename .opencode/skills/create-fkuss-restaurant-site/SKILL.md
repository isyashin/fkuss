# Создать сайт ресторана Fkuss

Собери готовый сайт ресторана, не смешивая данные клиента с кодом Fkuss.
Для реального ресторана меняй только `sites/<slug>/content/**`. Не редактируй
`template/src`, `template/scripts`, `platform` и эксплуатационные скрипты.

## Обязательные правила

- Цены и состав блюд бери из входных материалов или Яндекс.Еды. Не выдумывай их.
- Контакты и часы подтверждай по официальному сайту/соцсетям либо у владельца.
- Не публикуй заглушки, неподтверждённые контакты и несуществующие изображения.
- Не копируй случайные фотографии из поиска. Используй материалы владельца,
  официальные ресурсы ресторана или изображения из его карточки Яндекс.Еды;
  сомнения по правам перечисли до публикации.
- Секреты живут только в `secrets/sites/<slug>.env`; в content допустимы лишь
  имена переменных вида `*Ref`.
- Seed, деплой и другие изменения внешнего состояния выполняй только после
  сводки и подтверждения пользователя.

## Маршрут работы

1. Определи slug, целевой домен и каталог `sites/<slug>/content`. Не используй
   `template/content` для клиента, если пользователь явно не просит изменить
   демонстрационный ресторан.
2. **Собери манифест**: опросник — в
   [interview.md](references/interview.md), схема —
   `template/scripts/schemas/site-input.ts`. Источник меню (Еда-URL или
   папка) фиксируется в манифесте как контракт прогона.
3. Для ссылки Яндекс.Еды — инжест с лестницей устойчивости (workflow.md)
   через `assemble-content.ts`: retry → адаптация парсера → фолбэк размеров
   фото → `--browser` (Playwright; капча-сервисы и чужие сессии запрещены).
   Для папки — assemble-content сам нормализует изображения и подставит
   данные манифеста. Полный фейл — диагностический отчёт и стоп до решения
   пользователя; к другому источнику без его явной команды не переключаемся.
4. Если нужны адрес, телефон, часы, официальный сайт или соцсети, проведи
   исследование по [research-and-sources.md](references/research-and-sources.md)
   — `source-report.json` assemble пишет из манифеста автоматически.
5. VALIDATE: `npx tsx scripts/validate-content.ts <dir>` — без БД. Красный —
   чиним контент/манифест, деплоя не будет.
6. Покажи сводку (REVIEW): источники, статистика меню, контакты с
   confirmedBy, решения, пробелы. После подтверждения запиши `approvedBy`
   в манифест и пересобери архив — без него `provision-site.sh` не стартует.
7. Разворачивай сайт лишь по явному запросу:
   `provision-site.sh <slug> <content.tar.gz>` на сервере — он сам делает
   deploy/seed/владельца/платформу/Caddy/проверки; пошаговая последовательность
   (fallback для отладки) — в [deploy-runbook.md](references/deploy-runbook.md).
   После деплоя проверь URL, заказ без реального списания, бронь, мобильную
   вёрстку и админ-вход.

Если Яндекс изменил API или включил защиту — реши по лестнице устойчивости
(workflow.md): retry → адаптация парсера → фолбэк размеров фото →
`--browser` (Playwright-рендеринг; капча-сервисы и чужие сессии запрещены).
Полный фейл — диагностический отчёт и стоп до решения пользователя.
К другому источнику (папка/файл) без его явной команды не переключаемся.
