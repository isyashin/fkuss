# Публикация нового сайта

## Сначала определить серверную раскладку

- **Legacy shared-PG:** общий PostgreSQL `template-db-1`, сеть
  `template_default`, `<RESTO_BASE>/src`, `sites`, `registry.json`, управляемые
  блоки `resto-site-begin/end` в Caddy. Здесь работает `provision-site.sh`.
- **Новый dev с отдельной DB каждого ресторана:** использовать
  `docs/TOPOLOGY-OPERATIONS.md`. Автоматическое создание DB/compose этой
  раскладки не входит в PR #32. `RESTO_TOPOLOGY` блокирует legacy-команду.

Не переносить команду между серверами по совпадению имени ресторана. Не
подставлять чужой DB-контейнер и не пересевать существующий сайт.

## Что проверить до публикации

1. Прочитать AGENTS.md, docs/ARCHITECTURE.md, docs/DEPLOY.md и фактическую
   топологию. Сверить активные checkout, контейнеры, порты, БД, env и Caddy.
2. Образы dev/prod собраны из main после merge. Для воспроизводимости указать
   `RESTO_IMAGE` и `MIGRATOR_IMAGE` с immutable тегами одного release SHA.
   Не собирать релиз из рабочей ветки или чужого checkout.
3. BUILD в отдельный каталог: `assemble-content.ts --input ... --out ...`.
   Папка источника и результат не пересекаются. Источник не меняется; в
   результат копируются только JSON контента и изображения, без `.env`.
   Для ручного browser-fallback Еды передать `--browser` в assemble.
4. `validate-content.ts <content>`: схема, дубли ID, изображения и readiness.
   Проверить два меню, модификаторы и цены, если они есть в источнике.
5. Сводка владельцу: контакты, часы, доставка, лояльность, пробелы, а также
   **platform.ownerEmail**, **tariffId**, **initialKopecks**. Email кабинета
   отдельно от публичного email ресторана; тариф должен существовать. Стартовый
   баланс задаётся в копейках явно, 0 допустим. Автоматического подарка 3000 ₽ нет.
6. `approvedBy` записать только после подтверждения этой сводки пользователем.
   При `publishWithGaps=false` устранить все пробелы. Пересобрать архив с
   корнем `content/`, манифестом и source-report. Отдельно разрешить сам деплой.

## Legacy: проверка и публикация

На сервере, после инвентаризации и согласования:

```bash
export RESTO_BASE=/srv/resto
export RESTO_IMAGE=resto-template:release-SHA
export MIGRATOR_IMAGE=resto-template-migrator:release-SHA
bash "$RESTO_BASE/src/scripts/provision-site.sh" restaurant /path/content.tar.gz --dry-run
bash "$RESTO_BASE/src/scripts/provision-site.sh" restaurant /path/content.tar.gz
```

Заменить пути, slug и SHA реальными. `--dry-run` распаковывает только временный
каталог, проверяет архив, полный content в migrator без сети, тариф, владельца
и отсутствие чужих ресурсов. БД, сайт и Caddy не меняются. Локальный lock-файл
и временные файлы проверки допустимы.

Публикация держит общий flock и журнал `<RESTO_BASE>/provisions/<slug>.json`
(600, без секретов). Существующие каталог/DB/роль/строка платформы без своего
журнала не принимаются. Выполненные этапы не повторяются; готовая публикация
проверяет HTTP/HTTPS, сохраняя меню, настройки, пароль и баланс. Другой архив
для того же сайта отклоняется. Для изменений используется отдельный процесс
обновления с backup, а не повторный seed.

Регистрация Site/OwnerAccount/стартового ledger атомарна и защищена dedupe key.
Канонический домен берётся из манифеста. Caddy проходит validate до замены и
восстанавливается при неудачном reload штатным sync-caddy. Ручного дописывания
блоков в этой команде нет. Пароль владельца остаётся в приватном `.env`;
не печатать его или site key в отчёт, чат, командную строку и логи.

## Приёмка

Автоматический smoke проверяет HTTP, PWA-иконку, HTTPS и вход владельца с
отзывом временной сессии. Изоляция проверяется настоящим новым DB-пользователем
на таблице соседнего tenant: принимается только SQLSTATE 42501. Если соседей
нет, выводится 0 проверок, доказательства изоляции ещё нет.

Отдельно, в согласованной QA-копии: мобильная/desktop витрина, два меню,
смешанный заказ, модификаторы, адрес/геозона, часы и предзаказ, бронь,
админ-вход/права, уведомления и push на физических устройствах. Сам provision
не создаёт заказ и не отправляет сообщения в живые каналы ради smoke.

## Отказ и откат

Сохранить журнал и диагностику; исправить конкретную причину. Возобновлять
только тот же архив. Частичный контент с отличиями не заменяется автоматически.
Не удалять журнал ради обхода проверки. Не применять ручные DROP/DELETE из
старых инструкций и не считать любой ненулевой код доказательством изоляции.

Только для **неиспользованной публикации**, созданной этим журналом:

```bash
CONFIRM=YES bash "$RESTO_BASE/src/scripts/provision-site.sh" restaurant --rollback
```

Откат отказывает при заказах, клиентах, бронях, бонусах, платежах, счетах,
постороннем ledger, изменении DB/platform-владения или роли с другой БД.
После остановки app повторно проверяет бизнес-данные; при позднем заказе
отказывается и запускает app обратно. Удаляет только свои ресурсы и tagged
cron-строки. Для используемого сайта нужен отдельный backup/decommission.
