# Systematic Debugging

Случайные исправления тратят время и создают новые баги.

**Железный закон: НИКАКИХ ИСПРАВЛЕНИЙ БЕЗ ИССЛЕДОВАНИЯ КОРЕННОЙ ПРИЧИНЫ.**

## Фаза 1: Исследование причины

1. **Прочитай ошибку полностью.** Stack trace, номера строк, коды ошибок.
   Найди строку ошибки поиском по коду.
2. **Построй короткий цикл обратной связи.** Одна команда, которая краснеет
   на симптоме пользователя и зеленеет, когда баг исправлен:
   - падающий тест (лучший вариант);
   - curl/скрипт против запущенного сервера;
   - CLI-вызов с фикстурой;
   - Playwright-сценарий для UI-бага.
   Цикл должен быть быстрым и детерминированным. Нет воспроизведения —
   собирай данные, не гадай.
3. **Проверь недавние изменения**: `git log --oneline -10`, `git diff`.
4. **В многослойной системе** (API → сервис → БД, вебхук → обработчик)
   добавь логирование на границах компонентов и один прогон, показывающий,
   ГДЕ ломается. Затем копай конкретный компонент.
5. **Трассируй поток данных** к источнику плохого значения.
   Исправляй источник, не симптом.

СТОП: не переходи к фазе 2, пока не понятно, ПОЧЕМУ происходит ошибка.

## Фаза 2: Анализ паттерна

1. Минимизируй воспроизведение (убирай элементы, пока ломается).
2. Найди в кодовой базе похожий РАБОТАЮЩИЙ код.
3. Выпиши все отличия, даже «немогущие влиять».
4. Проверь зависимости, конфиг, окружение.

## Фаза 3: Гипотезы и проверка

1. Сформулируй 3–5 фальсифицируемых гипотез, ранжируй по вероятности
   и дешевизне проверки. У каждой — предсказание: «если причина X,
   то изменение Y даст Z».
2. Проверяй по одной, минимальным зондом, меняй одну переменную за раз.
3. Временные логи помечай уникальным префиксом `[DEBUG-xxxx]`,
   чтобы удалить одним поиском.

## Фаза 4: Исправление

1. Сначала падающий регрессионный тест (см. навык test-driven-development).
2. ОДНО исправление коренной причины. Никаких «заодно».
3. Прогон: целевой тест зелёный → весь набор зелёный, вывод чистый.
4. **Правило трёх**: 3 неудачных исправления — СТОП, это архитектурная
   проблема. Обсуди с пользователем, не пытайся исправить в 4-й раз.

## Красные флаги — вернись в фазу 1

- «быстро исправлю, разберусь потом»
- «попробую поменять X и посмотрим»
- несколько изменений за один прогон
- «это наверняка X» без воспроизведения
- «ещё одна попытка» после 2+ неудач

## Инструменты

Используй доступные инструменты чтения файлов, поиска по коду, запуска
команд и веб-поиска (документация по тексту ошибки).
