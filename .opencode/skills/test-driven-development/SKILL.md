# Test-Driven Development (TDD)

**Железный закон: НЕТ КОДА ПРОДАКШЕНА БЕЗ ПАДАЮЩЕГО ТЕСТА СНАЧАЛА.**

Написал код до теста? Удали его. Не «оставь как референс» — удали.
Реализуй заново от тестов.

В проекте TDD **обязателен** для всей логики денег: суммы заказа, доставка,
бонусы (начисление/списание/сторно), скидки, платежи и вебхуки.

## Цикл

### RED — падающий тест

- Одно поведение на тест, имя описывает поведение.
- Тестируй реальный код, моки — только когда без них никак.
- **Обязательно запусти и увидь падение** по ожидаемой причине
  (фича отсутствует, а не опечатка). Тест сразу зелёный — ты тестируешь
  существующее поведение, исправь тест.

### GREEN — минимальный код

- Простейший код, чтобы тест прошёл. Хардкод допустим — почистим потом.
- **Обязательно запусти**: целевой тест зелёный + ВЕСЬ набор зелёный.
- Падает целевой — правь код, не тест. Упали другие — чини регрессии сразу.

### REFACTOR — чистка

- Только после зелёного. Без нового поведения. Тесты зелёные на каждом шаге.
- Упало при рефакторинге — откати, делай меньше шаги.

### Повтор

Следующий тест — следующее поведение. Вертикальные срезы:
RED→GREEN по одному поведению, а не «все тесты, потом вся реализация».

## Частые отговорки → ответы

| Отговорка | Реальность |
|---|---|
| «слишком просто для теста» | Простой код ломается. Тест — 30 секунд. |
| «напишу тест после» | Тест-после сразу зелёный и ничего не доказывает. |
| «уже проверил вручную» | Нет записи, нельзя перезапустить, легко забыть. |
| «жаль удалять работу» | Sunk cost. Код без тестов — техдолг. |
| «существующий код без тестов» | Добавляй тесты на тот код, который трогаешь. |

## Чек-лист перед завершением

- [ ] Каждая новая функция имеет тест
- [ ] Видел падение каждого теста до реализации
- [ ] Падение было по ожидаемой причине
- [ ] Минимальный код для прохождения
- [ ] Весь набор тестов зелёный, вывод чистый
- [ ] Покрыты граничные случаи и ошибки

Не все галочки — это не TDD. Начни заново.

## Когда застрял

- Не знаешь, как тестировать — напиши желаемый API, начни с assert'а.
- Тест слишком сложный — упрости дизайн.
- Нужно мокать всё — код слишком связан, внедри зависимости.
