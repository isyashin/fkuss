# BILLING.md — биллинг сайтов и платформа владельца

Сайты ресторанов продаются по подписке. Документ описывает биллинг,
метрики и админку владельца платформы. Целевой формат; детали
уточняются на этапе 12 (см. `docs/PLAN.md`).

## Сущности платформы

- **Site**: slug, домены, баланс (₽), тариф, состояние
  (`active | grace | suspended`), site key (для API метрик),
  версия образа, дата создания.
- **Tariff**: название, цена ₽/мес, лимиты (если появятся).
- **Invoice**: номер, сайт, сумма, статус (выставлен/оплачен/отменён),
  PDF-файл, реквизиты.
- **Payment**: счёт, сумма, провайдер (ЮKassa), статус, дата.
- **MetricSnapshot**: сайт, дата, заказы (count, sum), брони (count),
  просмотры (count). Агрегаты — без персональных данных гостей.
- **OwnerAccount**: владелец сайта (email + код, тот же механизм,
  что у гостей ресторана).

## Биллинг — правила (деньги → TDD)

1. **Списание**: ежедневно `тариф / 30` с баланса сайта (cron платформы).
2. **Уведомления владельцу сайта**: когда баланса хватает на 7 / 3 / 1 дней —
   email и/или Telegram (канал и адрес — в кабинете платформы).
   Одно уведомление на порог (не спамим ежедневно).
3. **Исчерпание**: баланс < 0 → `grace` (по умолчанию 3 дня, сайт работает,
   уведомления продолжаются) → `suspended`: Caddy отдаёт страницу-заглушку
   «сайт временно недоступен». Данные и контейнер НЕ удаляются.
4. **Реактивация**: оплата прошла → баланс пополнен → сайт автоматически
   возвращается в `active`.
5. **Пополнение**: 
   - онлайн — ЮKassa платформы (карта/СБП), webhook пополняет баланс;
   - PDF-счёт для юрлиц: реквизиты платформы в настройках, номер и дата
     автоматически, генерация PDF на сервере.
6. История всех операций с балансом — ledger (`BalanceTransaction`:
   charge / topup / adjustment), баланс вычисляется из ledger.
7. Ручные операции владельца платформы (корректировка баланса,
   приостановка, реактивация) — с обязательным комментарием, пишутся
   в ledger/журнал.

## Метрики

- Шаблон сайта: route handler считает просмотры страниц (бот-фильтр по
  User-Agent), агрегаты заказов и броней берутся из БД сайта.
- Отправка на платформу: раз в 6 часов + при старте контейнера,
  `POST /api/metrics` с заголовком `X-Site-Key`. Повторы при недоступности
  платформы (очередь в БД сайта, без потери данных).
- Платформа хранит снапшоты и строит графики по сайту и сводные по всем.

## Админка владельца платформы

- Список сайтов: состояние, баланс, «хватит на N дней», тариф, домен,
  версия, последний снапшот метрик.
- Карточка сайта: графики (заказы, суммы, визиты, брони), история счетов
  и оплат, ledger баланса, ручные операции, кнопка экспорта.
- Сводный дашборд: активные сайты, MRR (платный остаток в пересчёте),
  суммарные заказы/выручка ресторанов.

## Кабинет владельца сайта

- Баланс, «хватит до <дата>», пополнить (ЮKassa), скачать счёт (PDF).
- Метрики своего сайта, история оплат.
- Экспорт сайта (архив), смена канала уведомлений.

## Экспорт сайта

- Кнопка в платформе → на хосте выполняется скрипт: `content/` + `pg_dump`
  базы сайта + `images/` → tar.gz в `backups/export/<slug>-<date>.tar.gz`.
- Ссылка на скачивание живёт 24 часа, затем файл удаляется.
- Экспорт — это точка выхода клиента: архив должен разворачиваться
  отдельно (инструкция в `docs/DEPLOY.md` на этапе 12).
