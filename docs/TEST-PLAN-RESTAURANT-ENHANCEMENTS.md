# План тестирования расширений сайта ресторана

Связанное ТЗ: `docs/TZ-RESTAURANT-ENHANCEMENTS.md`.

## 1. Цель и границы

Проверить реализацию Кимы независимо от разработки и доказать выполнение
каждого требования ТЗ. Проверка включает код и схемы, миграцию, unit и
integration-тесты, API, мобильный E2E, сборку и ручной smoke-тест.

Тестировщик не исправляет найденные дефекты в ходе приёмки. Находки сначала
фиксируются в `тестировщик/журнал.md` и обсуждаются с владельцем. GitHub issue
создаётся только после подтверждения владельца.

## 2. Условия начала приёмки

- Кима сообщает, что реализация завершена или готов отдельный этап.
- Доступны список изменённых файлов и миграций.
- Рабочее дерево не содержит необъяснённых временных файлов и секретов.
- Указаны команды миграции и отката.
- Есть тестовая PostgreSQL, отдельная от production.
- Для внешнего API Яндекс.Еды есть mock/fixture; автотесты не ходят в сеть.
- Подготовлен тестовый ресторан с блюдами, группами добавок, логотипом,
  фоном, банкетами и несколькими вариантами доставки.

## 3. Стратегия

Проверка проходит воротами. При blocker или critical следующий этап не
считается принятым, пока дефект не исправлен и не проверен повторно.

### Ворота A — статический аудит

1. Сопоставить diff с каждым разделом ТЗ.
2. Проверить Prisma и Zod-схемы, seed и документацию.
3. Проверить отсутствие секретов и данных конкретного ресторана в коде.
4. Проверить, что цены и доступность повторно читаются сервером.
5. Проверить tenant isolation путей файлов, настроек и запросов.
6. Проверить, что старые заказы остаются снимками и не пересчитываются.
7. Выполнить `git diff --check`.

### Ворота B — unit и integration

Из `template/` выполнить:

```bash
npm test
npm run lint
npm run build
```

Integration-тесты запускать только с тестовой `DATABASE_URL`. Перед тестами
зафиксировать число пройденных и пропущенных тестов. Пропуск обязательного
сценария не считать успехом.

### Ворота C — миграция

Проверить на копии старой БД:

1. Зафиксировать контрольные значения блюд, модификаторов, настроек и заказов.
2. Применить миграцию штатной командой проекта.
3. Проверить сохранность старых цен, доступности, заказов и их сумм.
4. Проверить безопасные значения новых полей.
5. Выполнить seed и убедиться, что бизнес-данные не удалились.
6. Проверить описанный путь отката на отдельной копии.
7. Повторно применить допустимые идемпотентные операции.

### Ворота D — API и серверная безопасность

Все денежные проверки выполнять с подменёнными клиентскими данными. Сервер
должен либо пересчитать итог, либо отклонить запрос.

### Ворота E — мобильный E2E

Из `template/` выполнить:

```bash
npx playwright test
```

Основной профиль — 360 px и мобильный WebKit. Дополнительно проверить Chromium
desktop. Снять скриншоты ключевых состояний: главная, меню, карточка блюда,
корзина, выбор времени, банкеты, фон, установка PWA и ошибки.

### Ворота F — ручной smoke

Проверить три темы, клавиатурную навигацию, состояния загрузки/ошибки/пустого
списка, контраст, зоны касания и реальные переходы между страницами.

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| SYNC-01 | Первая успешная синхронизация | Позиции сопоставлены по внешним ID, время успеха сохранено |
| SYNC-02 | Блюдо стало недоступно | Оно скрыто на витрине и запрещено сервером заказа |

## 5. Регресс

Обязательно повторно проверить:

- оформление заказа без оплаты и с mock-оплатой;
- серверный пересчёт, минимальную сумму и зоны;
- бонусы: начисление, списание, отмену и сторно;
- авторизацию гостя и историю заказов;
- бронирование и расписание;
- уведомления и сохранение заказа при падении отдельного канала;
- вход и guard админки;
- CRUD меню, страниц, галереи, акций и настроек;
- три пресета темы;
- биллинг и метрики платформы, если изменён общий код.

## 6. Нефункциональные проверки

- На 360 px нет горизонтального скролла и перекрытия sticky-элементов.
- Все основные зоны касания не меньше 44×44 px.
- LCP главной и меню не деградировал заметно из-за фона и полного меню.
- Изображения имеют размеры, lazy loading и alt.
- Клавиатурный фокус виден, диалоги удерживают фокус и закрываются.
- Ошибки синхронизации и загрузки не раскрывают внутренние детали.
- Один ресторан не получает файлы, настройки или данные другого.
- Повторный job и webhook остаются идемпотентными.

## 7. Severity и решение о выпуске

- **blocker**: сайт не стартует, миграция теряет данные, утечка секрета.
- **critical**: нельзя оформить заказ, неверная итоговая сумма, нарушена
  изоляция ресторанов.
- **major**: неверные стопы, цены, интервалы, модификаторы или PWA-иконки.
- **minor**: неудобство с рабочим обходом, локальная ошибка интерфейса.
- **trivial**: косметика без влияния на сценарий.

Выпуск запрещён при открытых blocker/critical и при красных обязательных
тестах. Major требует явного решения владельца. Minor/trivial можно вынести в
бэклог после фиксации в журнале.

## 8. Итоговый отчёт тестирования

Отчёт должен содержать:

- проверенную ревизию и окружение;
- результат каждого из ворот A–F;
- число пройденных, упавших и пропущенных тестов;
- таблицу требований с доказательствами;
- найденные дефекты и severity;
- результат проверки миграции и отката;
- скриншоты мобильных ключевых сценариев;
- остаточные риски;
- решение: `принято`, `принято с ограничениями` или `не принято`.
