# Техническое задание: синхронизация меню и развитие витрины ресторана

## 1. Назначение

Доработать мультитенантный шаблон сайта ресторана: добавить регулярную
синхронизацию доступности и цен с Яндекс.Едой, расширить управление ценами,
доставкой, модификаторами, главной страницей, банкетами, фоном и PWA.

Документ предназначен для автономной реализации через OpenCode. Перед началом
работы агент обязан прочитать корневой `AGENTS.md`, затем только относящиеся к
задаче документы: `docs/PLAN.md`, `docs/ARCHITECTURE.md`,
`docs/CONTENT-SCHEMA.md`, `docs/DEPLOY.md`, а для денежных изменений также
`docs/PAYMENTS.md`.

## 2. Неподлежащие изменению правила проекта

1. Контент конкретного ресторана не вшивать в код. Начальные данные находятся
   в `template/content/`, рабочие данные после seed — в БД.
2. Секреты хранить только в `secrets/` и переменных окружения. Не выводить их в
   логи, тесты, ответы и репозиторий.
3. Деньги, цены, доставка, модификаторы и итог заказа реализуются через TDD:
   сначала падающий тест, затем минимальный код.
4. Сервер заново получает цены и доступность из БД. Клиентским суммам и
   признакам доступности не доверять.
5. Изменения должны быть обратимо совместимыми с существующими ресторанами и
   заказами.
6. Mobile first от 360 px, зоны касания не менее 44×44 px.
7. Не рефакторить несвязанный код. При изменении статуса или этапов обновить
   `docs/PLAN.md` в том же наборе изменений.
8. Не коммитить секреты. Перед коммитом проверить `git diff` и список файлов.

## 3. Исходное состояние

- `template/scripts/ingest-yandex-eda.ts` выполняет одноразовый импорт через
  неофициальный API Яндекс.Еды.
- `Dish` хранит одну цену `price` и один признак `available`.
- Группы `optionsGroups` при импорте превращаются в плоский список
  модификаторов, ограничения групп теряются.
- Серверный расчёт уже суммирует выбранные модификаторы. Наблюдаемый баг с
  соусами сначала нужно воспроизвести тестом; вероятные причины — данные,
  идентификаторы или версия развёрнутого приложения.
- Время доставки хранится в `Order.desiredTime` как свободная строка.
- Полное меню находится на `/menu`; на главной есть только популярные блюда.
- PWA-манифест и интерфейс установки уже есть, но генерацию и обновление иконок
  из логотипа нужно проверить и завершить.

## 4. Порядок реализации

Работать этапами. После каждого этапа запускать относящиеся к нему тесты. Не
начинать следующий этап при красных тестах.

1. Документация, модели данных и миграция.
2. Синхронизация Яндекс.Еды.
3. Источники цен и коэффициенты.
4. Группы модификаторов и несколько соусов.
5. Интервалы и стоимость доставки.
6. Главная страница и банкеты.
7. Фоновое изображение.
8. PWA-иконки и состояние без сети.
9. Полный регресс, сборка и обновление `docs/PLAN.md`.

## 5. Модели данных и миграция

### 5.1. Блюда и модификаторы

Добавить данные, эквивалентные следующим полям. Конкретные имена можно
адаптировать к существующему стилю Prisma, но смысл сохраняется:

- источник позиции: `manual | yandex`;
- внешний ID Яндекс.Еды для блюда, категории, группы и модификатора;
- базовая цена из Яндекс.Еды;
- ручная цена;
- индивидуальный режим цены: `inherit | yandex | manual | coefficient`;
- индивидуальный коэффициент в процентах;
- ручная доступность администратора;
- доступность по данным Яндекс.Еды;
- время последнего успешного обновления позиции;
- группы модификаторов с `minSelected`, `maxSelected`, позицией и названием;
- возможность ручной цены отдельного модификатора.

Итоговая доступность связанного блюда:

`manualEnabled && yandexAvailable`.

Ручные блюда от Яндекс.Еды не зависят. Временное отсутствие позиции в ответе
не удаляет строку и историю.

### 5.2. Настройки синхронизации и цен

В настройках ресторана добавить:

- URL или `placeSlug` Яндекс.Еды;
- включение синхронизации;
- периодичность;
- глобальный режим цены;
- глобальный коэффициент;
- время, статус и краткую ошибку последней попытки;
- время последней успешной синхронизации.

### 5.3. Заказы и доставка

Вместо свободной строки предусмотреть структурированные данные:

- `deliveryMode`: `asap | scheduled`;
- локальная дата доставки;
- начало и конец интервала;
- часовой пояс ресторана;
- снимок стоимости выбранного варианта.

Старое поле можно временно сохранить для обратной совместимости и заполнения
человекочитаемого текста. Старые заказы не изменять.

### 5.4. Требования к миграции

- Существующие `price` и `available` сохранить.
- Новые поля получить безопасные значения по умолчанию.
- До первой успешной синхронизации сайт продолжает работать по старым данным.
- Миграция не меняет `OrderItem.price`, суммы и историю заказов.
- Обновить seed, Zod-схемы, `docs/CONTENT-SCHEMA.md` и тестовые данные.
- Подготовить понятный путь отката БД до развёртывания.

## 6. Синхронизация с Яндекс.Едой

### 6.1. Запуск

- Фоновый запуск по настраиваемому расписанию.
- Ручная кнопка «Синхронизировать сейчас» в админке.
- Защищённый job endpoint для cron по существующему паттерну проекта.
- Блокировка одновременных запусков для одного ресторана.
- Ограниченный retry с backoff при временных ошибках.

### 6.2. Поведение

- Сопоставлять позиции по внешним ID, а не по названию.
- Обновлять доступность, базовую цену и структуру модификаторов.
- Переименование и перенос категории не создают дубликат блюда.
- Удалённая или пропавшая позиция не удаляется физически.
- При ошибке сохраняется последнее успешное состояние.
- Одна ошибка не должна скрыть всё меню.
- В логах не должно быть токенов, cookie и других секретов.

### 6.3. Админка

Показать переключатель, источник, расписание, последний запуск, последний
успех, результат, кнопку ручного запуска и понятную ошибку. После длительной
ошибки предусмотреть заметное предупреждение администратору.

Неофициальный API Яндекс.Еды считать нестабильной внешней зависимостью:
изолировать клиент в отдельном модуле, добавить timeout и тестируемый интерфейс.

## 7. Цены

### 7.1. Режимы

Глобально для меню и индивидуально для блюда доступны:

1. Цена Яндекс.Еды без изменений.
2. Ручная цена.
3. Цена Яндекс.Еды плюс или минус процент.

Индивидуальная настройка приоритетнее глобальной. Действие «Использовать общую
настройку» переводит блюдо в режим `inherit`.

### 7.2. Формула

При коэффициенте итог равен:

`round(yandexPrice × (1 + percent / 100))`.

Округление математическое до целого рубля. Отрицательная итоговая цена
запрещена. Если базовой цены Яндекс.Еды нет, режимы `yandex` и `coefficient`
недоступны, а админка показывает причину.

Общий коэффициент применяется также к платным модификаторам. Если у
модификатора задана собственная ручная цена, она имеет приоритет.

В админке показывать цену Яндекс.Еды, выбранный режим, ручную цену или процент
и итоговую цену. Сервер заказа использует только рассчитанную цену из БД.

## 8. Модификаторы и соусы

- Не объединять группы Яндекс.Еды в плоский список.
- Для каждой группы сохранить минимальное и максимальное число вариантов.
- UI выбирает radio при максимуме 1 и checkbox при максимуме больше 1.
- Нельзя добавить блюдо, если не выполнен обязательный минимум.
- Каждый выбранный соус или модификатор учитывается в цене.
- Сервер отклоняет неизвестные, чужие, повторные сверх лимита и недоступные ID.
- Корзина, заказ, уведомление и админка показывают каждый выбранный вариант и
  его цену.
- При количестве блюда больше 1 стоимость набора модификаторов умножается на
  количество блюда, как и сейчас.

Обязательный тест: три выбранных соуса увеличивают сумму ровно на сумму цен
трёх соусов и сохраняются в снимке заказа.

## 9. Доставка

### 9.1. Настройки

Для каждого варианта доставки задаются:

- название;
- режим `asap` или `scheduled`;
- доступные дни и часы;
- длительность интервала;
- минимальное время до доставки;
- глубина предварительного заказа в днях;
- стоимость;
- порог бесплатной доставки;
- исключения по датам.

Учитывать часовой пояс ресторана. Заказ на завтра можно оформить ночью, если
завтрашний интервал доступен.

### 9.2. Расчёт и проверка

- Интервалы генерирует сервер.
- Перед созданием заказа сервер повторно проверяет выбранный интервал.
- Прошедший, закрытый или несуществующий интервал отклоняется.
- При достижении порога вся стоимость выбранного варианта доставки становится
  нулевой, в том числе для срочной доставки.
- Правила доставки и самовывоза независимы.
- Существующие зоны сохраняются. Если используются и зона, и вариант времени,
  в админке должна быть однозначно видна итоговая стоимость; не допускать
  двойного неявного начисления.
- Дата, интервал и снимок цены сохраняются в заказе, уведомлениях и админке.

## 10. Главная страница

- Первый экран содержит кнопки «Заказать с доставкой» и «Банкеты».
- Первая кнопка плавно прокручивает к полному меню на главной.
- Вторая открывает страницу банкетов и скрывается, если раздел отключён.
- Сразу после первого экрана размещается полное меню.
- «О нас» и «Контакты» всегда находятся ниже меню.
- Старый `/menu` сохраняется как redirect на `/#menu`.
- Существующее бронирование не удалять; сохранить доступ к нему в шапке, если
  это не нарушает новую композицию.
- Переиспользовать существующий компонент меню, не создавать две расходящиеся
  реализации.

## 11. Банкеты

Добавить включаемый раздел с отдельной страницей и настройками:

- заголовок и описание;
- список залов;
- название, вместимость и описание каждого зала;
- упорядоченная галерея;
- условия;
- опциональные цены;
- телефон или другой контакт;
- текст и ссылка CTA.

При выключении раздела страница возвращает 404, а кнопки и ссылки скрываются.
Контент каждого ресторана изолирован и не вшит в код.

## 12. Фоновое изображение

В настройках темы добавить:

- включение;
- загрузку, замену и удаление изображения;
- режим `cover`;
- позицию;
- силу затемнения или светлой подложки;
- предварительный просмотр;
- отдельную возможность отключить фон на мобильных устройствах.

Изображение хранить в tenant-specific content volume, проверять MIME и размер,
оптимизировать через `sharp`, не принимать SVG. Старый файл удалять безопасно
только после успешной записи нового. Обеспечить контраст текста и кнопок.

## 13. PWA

- Сохранить существующую кнопку установки.
- Android: `beforeinstallprompt`.
- iOS: инструкция «Поделиться» → «На экран “Домой”».
- Иконка — логотип конкретного ресторана.
- Генерировать PNG 192×192, 512×512 и apple-touch-icon 180×180 с безопасными
  полями и fallback-иконкой платформы.
- При замене логотипа обновлять URL или версию иконок, чтобы обойти кэш.
- Если приложение уже установлено, кнопку не показывать.
- Полный офлайн-кеш меню не нужен: нельзя показывать устаревшие цены и
  стоп-лист. Без сети показывать понятный экран «Нет подключения».

## 14. Тесты и критерии приёмки

Минимальный обязательный набор:

1. Успешная синхронизация, стоп, возврат позиции и переименование.
2. Ошибка и timeout Яндекс.Еды сохраняют последнее успешное состояние.
3. Ручные блюда не скрываются синхронизацией.
4. Три режима цены, `inherit`, приоритет блюда и округление.
5. Коэффициент модификатора и его ручное переопределение.
6. Три соуса полностью учитываются клиентом и сервером.
7. Сервер отклоняет подменённые ID и нарушение min/max.
8. Доставка ASAP, будущий интервал и заказ на завтра ночью.
9. Порог бесплатности обнуляет стоимость выбранного варианта.
10. Сервер отклоняет устаревший интервал.
11. Меню находится на главной, `/menu` ведёт на `/#menu`.
12. Отключённые банкеты скрыты и возвращают 404.
13. Загрузка, замена и удаление фона.
14. PWA-манифест использует иконки текущего ресторана.
15. Мобильный E2E на ширине 360 px: меню → модификаторы → корзина → интервал
    → заказ.
16. Регресс существующих тестов оплаты, лояльности, бронирования и админки.

Команды проверки из `template/`:

```bash
npm test
npm run build
npx playwright test
```

Интеграционные тесты запускать только с тестовой `DATABASE_URL`. Внешний API в
автотестах мокать; тесты не должны зависеть от доступности Яндекс.Еды.

## 16. Формат работы агента OpenCode

Перед кодом агент должен:

1. Прочитать указанные документы и релевантные файлы реализации.
2. Проверить `git status` и не затронуть чужие изменения.
3. Составить короткий поэтапный план и обновить `docs/PLAN.md`.
4. Начать с падающих тестов моделей, цен, модификаторов и доставки.

После каждого этапа агент сообщает: что сделано, какие тесты запущены, что
остаётся и нужен ли выбор пользователя. Не скрывать ошибки и не объявлять этап
готовым при красных тестах. Не пушить изменения без явного разрешения владельца.
