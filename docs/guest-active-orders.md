# Заказ гостя после оформления

## Поведение

После ответа сервера нижняя панель показывает заказ и его статус. Состав заказа
больше не редактируется: он берётся из сохранённых OrderItem, включая добавки,
цены и названия меню. Новый выбор блюд создаёт отдельную корзину. Если активных
заказов несколько, нажатие открывает список. Доставка, скидка бонусами и итог
всегда берутся с сервера; значения из текущего меню не подменяют историю.

Детали на мобильном занимают весь экран, содержимое прокручивается отдельно.
Кнопка назад/системный Back закрывает детали. На десктопе это диалог. Кнопка
звонка ресторану доступна и при ошибке загрузки. Устройства с шириной 360 px
поддерживаются; активные кнопки не меньше 44 px, учтена нижняя safe area.

Заказ исчезает спустя пять секунд после серверного подтверждения `delivered`
для доставки, `issued` для самовывоза либо `cancelled`. Оплата и выполнение
заказа — разные состояния: `paid`, `pending`, `failed`, `ready` и передача
курьеру не очищают заказ. Другие заказы и новая корзина при этом сохраняются.

## Серверные данные и доступ

- `GuestOrderSession`: хеш случайного 48-байтового токена, срок жизни.
- `GuestCheckout`: пара sessionId/requestKey, хеш нормализованного запроса,
  связь с Order и платёжная ссылка. Уникальны пара sessionId/requestKey и orderId.
- Cookie `resto_guest_orders`: HttpOnly, SameSite=Lax, Path=/, Secure при HTTPS,
  без Domain. Срок 60 дней, обновляется при последующих оформлениях.
- `POST /api/order/session`: только тот же Origin; создаёт/продлевает браузерный
  доступ перед отправкой. Создание cookie сериализовано Web Locks между вкладками.
- `GET /api/order/active`: краткие статусы только для текущей сессии или покупателя.
  `known` ограничен 100 идентификаторами и не предоставляет права доступа.
- `GET /api/order/active/[id]`: полный снимок только владельцу, чужому — 404.
- Все ответы `/api/order/*`: private, no-store; service worker использует сеть.
  Cookie также запрещает кэширование персонализированной HTML-витрины.
- Logout отзывает анонимную сессию, удаляет cookie и локальную панель.
  У других устройств и пользователей доступ не меняется.

Регистрация гостя не требуется. Данные привязаны к конкретному браузеру/PWA
и сайту ресторана. Другой браузер, приватный режим, очистка данных или истечение
cookie не восстанавливают анонимный доступ. Для переноса между устройствами нужен
вход в аккаунт, к которому заказ был привязан при оформлении. Отдельные хранилища
Safari и установленной PWA не считаются одним браузерным хранилищем.

## Повтор запроса и оплата

Ключ вычисляется из поколения корзины и SHA-256 её полного запроса. При повторе
того же оформления используется прежний ключ, включая случай потери ответа.
Сервер проверяет принадлежность ключа сессии и соответствие тела. Повтор читается
до проверки новых цен/доступности блюд; advisory lock внутри транзакции исключает
двойное создание заказа, списание бонусов и событие. Повторные обращения не
создают платёж и не повторяют уведомления. Старый клиент без ключа поддерживается,
но защиту повтора получает только обновлённый checkout.

Создание платежа находится вне транзакции с БД. Пока оно идёт, повтор показывает
сохранённый заказ; ссылка появляется после успешного ответа провайдера. При
отказе провайдера остаётся заказ с `failed`, существующая компенсация бонусов
выполняется один раз. Автоматическая повторная оплата и отмена не добавлены:
гость видит ошибку и может позвонить ресторану. Действующий webhook и ручная
работа сотрудника со статусами не изменены.

Подтверждение заказа записывается до навигации к провайдеру. Запоздалый ответ
после закрытия оформления не уводит гостя из новой корзины и не очищает её.
В localStorage — только существующая корзина, ключи попыток, короткие статусы
и подтверждения уже показанного завершения. Адрес, телефон, токен доступа,
комментарий и ссылка на оплату туда не попадают.

## Связь и PWA

Один опрос на вкладку, интервал 15 секунд при активных заказах/отправке;
скрытая вкладка не опрашивается. Возврат в окно и online запускают обновление.
Запрос завершается по таймауту; ошибки сохраняют последнюю известную информацию
с явной пометкой и кнопкой обновления. Пустые ответы не стирают известный заказ.
Только подтверждённое сервером завершение можно скрыть; значения из старого
кэша сами этого не делают. Web Push гостю эта задача не добавляет.

Физическая приёмка на iPhone и Android: оформить, закрыть/снова открыть
установленную PWA, перейти к оплате и вернуться, выключить/включить сеть,
закончить заказ со стороны сотрудника. Автотесты Chromium/WebKit и настоящий
service worker проверяют программные сценарии, физический телефон не заменяют.

## Выпуск и откат

Аддитивная миграция 0014 не изменяет прежние столбцы/строки Order. До production
восстановить копии всех tenant-БД, применить миграции дважды, сравнить прежние
таблицы и запустить приложение. Затем обновлять рестораны по одному, сохраняя
настройки, env, меню и секреты. Production не использовать для искусственных
заказов/списаний; полный CJM выполнять на изолированных копиях.

При откате вернуть прежний runtime-образ; новые таблицы можно оставить.
Старое приложение их не использует. Не откатывать целиком production-БД,
поскольку это уничтожит реальные заказы, полученные после выпуска.
