# Issue: Мониторинг ресурсов в админке платформы (общий и по сайтам, с историей)

## Цель

В админке платформы (`platform/admin`) видеть нагрузку сервера в целом и по каждому сайту с историей — чтобы вовремя понимать, когда увеличивать ресурсы (RAM/диск/CPU).

Контекст: прод-сервер 3,3 ГБ RAM / 8 CPU / 30 ГБ. По замерам сайт Next.js ест ~65 МБ в простое, пик ~350 МБ. Комфортная ёмкость ~12 сайтов. Нужен ранний сигнал приближения к потолку.

## Скоп работ

**Сбор метрик хоста (агент на сервере):**
- Cron-скрипт на сервере (раз в 5 мин): RAM (used/total), диск (used/total), load average, данные `docker stats` по каждому контейнеру (RAM, CPU%)
- Отправка на платформу: `POST /api/host-metrics` (X-Site-Key или отдельный HOST_KEY)

**Хранение (платформа):**
- Таблица `HostMetricSnapshot(ts, ramUsed, ramTotal, diskUsed, diskTotal, load1)`
- Таблица `ContainerMetricSnapshot(ts, name, ramBytes, cpuPercent)` — привязка контейнера к сайту по имени (`<slug>-app-1`)

**UI в админке платформы:**
- Дашборд: текущие RAM/диск/load + «заполнено на X%», график за 7/30 дней
- В карточке сайта: его контейнер — RAM/CPU с историей
- Порог-подсказка: «RAM заполнена на 80% — пора расширять» (подсветка от 75%)

**Опционально:** уведомление владельцу платформы (email/Telegram) при RAM > 85% или диск > 90%.

## Критерии приёмки

- [ ] В админке платформы видно текущую нагрузку сервера (RAM/диск/load)
- [ ] По каждому сайту — потребление RAM/CPU его контейнера
- [ ] История минимум за 30 дней с графиком
- [ ] Индикация приближения к потолку (75%/85%)
- [ ] Сбор не влияет на работу сайтов (cron, таймауты, без блокировок)

## Технические заметки

- Сбор через `docker stats --no-stream --format json` (без дополнительных демонов)
- Ретенция: сырые точки 7 дней, часовые агрегаты 90 дней (рост БД контролируемый)
- Связка контейнер↔сайт: `<slug>-app-1` (наше именование в deploy.sh)
