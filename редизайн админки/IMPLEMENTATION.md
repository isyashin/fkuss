# Внедрение редизайна настроек: техническое задание

**Статус на 2026-10-04:** описано и проверено по коду; не реализовано. Макет находится в соседнем файле `settings-redesign-preview.html`. Этот документ предназначен агенту разработки, а не агенту наполнения сайта.

## 1. Результат, который нужно получить

Рабочая админка повторяет структуру и визуальный язык макета. Главная навигация содержит только «Заказы», «Брони», «Меню», «Настройки». Сотрудник редактирует меню без PIN. Настройки сайта, ресторана, доставки, связи, сотрудников и подписки находятся внутри «Настроек» и защищены правом `manage` (владелец либо сотрудник с действующей разблокировкой PIN). Ни одна действующая операция не исчезает при переносе. Изменения сохраняются в БД текущего ресторана, отражаются на витрине и переживают перезагрузку.

**Приоритет источников:** правила доступа, расчёт денег, серверная валидация, текущие данные ресторана и ограничения БД важнее демонстрационного поведения HTML. Макет определяет композицию, названия и основные взаимодействия. Все расхождения ниже решены явно; нельзя подставлять примерные значения HTML в рабочую БД.

Работу разделить на два независимых результата:

1. **Безопасное подключение интерфейса:** внешний вид и внутренняя навигация меняются; цены и проверка заказов работают по прежним правилам. Недостающие поля для действующих настроек показываются в рабочем редакторе.
2. **Изменение модели доставки:** после отдельной проверки данных ресторанов цена и доступность адреса переходят к зонам, вариант определяет время и при необходимости надбавку. Этот этап требует TDD и миграции. Не включать его незаметно вместе с первым результатом.

## 3. Навигация и поведение форм

Предпочтительная структура: `/admin/settings` открывает первый доступный экран; внутренние адреса `/admin/settings/contacts`, `/hours`, `/appearance`, `/pages`, `/gallery`, `/promos`, `/banquets`, `/print`, `/delivery`, `/payments`, `/booking`, `/pricing`, `/sync`, `/guest`, `/notifications`, `/team`, `/billing`. Общий layout рисует навигацию и проверяет `manage` до загрузки данных дочерней страницы. Для сотрудника без PIN оставить экран ввода PIN, для неавторизованного — вход. Саму проверку повторять во всех действиях/API; скрытая ссылка не защищает данные.

Текущие прямые маршруты `/admin/delivery`, `/admin/team` и другие не удалять до завершения переноса: сделать защищённые перенаправления или сохранить совместимые страницы. Обновить главную и мобильную навигацию в `admin-shell.tsx`: вторичные владельческие пункты не должны выглядеть отдельными рабочими разделами. Названия и порядок внутренних разделов брать из макета, но не копировать массивы с примерным контентом как источник данных.

Каждая страница загружает только свои данные. Сейчас `settings/settings-extra-sections.tsx` собирает почти все таблицы и биллинг при открытии настроек; после переноса запросы должны уйти в соответствующие страницы. Это уменьшит задержку и не позволит сбою платформы подписки ломать контакты ресторана.

Форма хранит серверный снимок, текущие значения, признак изменения, ожидание ответа и ошибку. Кнопка сохранения относится к видимому редактору. При попытке уйти с несохранёнными данными показать выбор «Остаться»/«Уйти». Отключить повторную отправку на время сохранения. При ошибке оставить введённые значения. После успешной записи обновить снимок из ответа сервера и нужные маршруты через `revalidatePath`.

Для самостоятельных действий нужен собственный результат: загрузка фото, удаление, запуск синхронизации, экспорт, пополнение. Нельзя выводить «Сохранено», если файл существует только в `blob:` URL. Если файл выбирается внутри формы с общей кнопкой, до неё показывать локальное превью, а окончательное состояние подтверждать только после успешной загрузки и обновления записи. Не оставлять прежний файл удалённым при неудачной замене.

## 4. Сохранение данных без потерь

Не подключать все вкладки к `saveSettings(settings)` из `settings/actions.ts`: функция валидирует и перезаписывает целиком `Settings(key=settings)`. Не строить полный объект из старых props страницы. Ввести небольшие серверные команды по разделам (`saveContacts`, `saveOpeningHours`, `saveAppearance`, `saveDeliveryConfiguration`, `savePaymentAndLoyalty`, `savePricingRules`, `saveNotificationChannels` и т. д.) с точными входными схемами Zod.

Общий внутренний helper для JSON-ключа должен **в транзакции** блокировать ключ, читать актуальное значение из БД, менять только разрешённый фрагмент, проверять его схемой и записывать результат. Не записывать результат разбора всего объекта через `settingsSchema.parse`: обычный `z.object` исключит поля, которых нет в схеме. При сохранении опираться на сырую актуальную запись и подменять в ней только проверенный фрагмент. Там, где один редактор меняет два ключа или таблицу вместе с JSON, обе записи входят в одну транзакцию. Применить сравнение исходного снимка редактируемого фрагмента с актуальным: при параллельной правке того же фрагмента показать конфликт и предложить обновить экран, не затирая чужие изменения. Правки разных разделов не конфликтуют.

Конкретные связанные операции:

- **Часы:** обновить `restaurant.schedule`, производный `workHours` и `settings.timezone` атомарно. Сохранение контактов не должно перезаписывать расписание из старого состояния формы.
- **Оформление:** обновить только `preset`, `accent`, `background` одного ключа `theme`; сохранить остальные поля темы. Разрозненные `saveTheme` + `saveBackground` не использовать как одну успешную операцию.
- **Цены:** изменение `settings.pricing` и `recomputePrices(tx)` в той же транзакции. Оплата и бонусы могут сохраняться отдельно без пересчёта меню. Суммы в заказах по-прежнему пересчитываются на сервере.
- **Доставка:** если редактор имеет одну кнопку, обновить `settings.delivery` и изменения строк `DeliveryOption` в одной транзакции. Сохранять стабильные ID существующих вариантов и не удалять их при пропуске скрытой части формы.
- **Банкеты:** добавить типизированное `banquets` со значениями по умолчанию в `settingsSchema` и `docs/CONTENT-SCHEMA.md`; переходить на адресное изменение `settings.banquets`. Сейчас `validateSettingsMutation` разбирает схему без `banquets`, и полная запись может потерять этот блок. Миграция в новый ключ только ради внешнего вида не нужна.
- **Синхронизация:** оставлять отдельный `saveSyncSettings`; запуск сейчас — отдельная операция, которая не зависит от несохранённых полей.

Таблицы `Page`, `Promo`, `GalleryImage`, `BanquetHall`, `AdminUser` изменять через адресные действия с ID и проверкой прав. Не превращать их в один большой JSON. Обработка файлов — в каталоге текущего tenant-а. Ключи ботов, платёжки и платформы не передавать в браузер и не записывать в настройки как значения: допустимы только уже предусмотренные имена переменных.

## 5. Право доступа и загрузки

`hasAdminPermission` даёт сотруднику `orders`, `bookings`, `menu`; `hasPermissionWithUnlock` расширяет `manage` после PIN. Использовать одинаковое правило для внутренних маршрутов, server actions и API. Сотруднику без PIN нельзя получать данные владельца через прямой адрес или вызов действия.

Исправить `api/admin/upload/route.ts`: сейчас проверка `actor.role === "staff" && section !== "dishes"` запрещает владельческие изображения даже сотруднику с действующей разблокировкой PIN. Для `dishes` требовать `menu`, для `logo`, `background`, `gallery`, `promos` — `manage`. Ограничение формата/размера и путь в `CONTENT_DIR` сохранить. Для звука оставить проверку `manage` в `api/admin/sound/route.ts`.

Отдельные действия сотрудников должны продолжать отзывать сессии при изменении роли, активности или пароля и не позволять отключить последнего активного владельца. Данные одного ресторана не должны попадать в БД или контент другого.

## 6. Доставка: два последовательных этапа

### 6.1. Первый выпуск интерфейса: прежний расчёт

Текущий `api/order/route.ts` при выбранном варианте доставки считает цену по `DeliveryOption.price/freeFrom` и пропускает проверку зон. Корзина и `lib/admin-order-edit.ts` действуют аналогично. Поэтому для первого выпуска нового редактора:

- Показать сохранённые цену и порог бесплатности варианта, дни недели, состояние, время, исключения. Эти поля нужны для честного редактирования текущей модели, хотя в HTML-макете цены варианта нет.
- Не заявлять в работающем интерфейсе «Стоимость берётся из зоны», пока сервер использует цену варианта. Если варианты активны, объяснить в редакторе, какая цена применяется.
- Встроить реальный `ZoneMap` и редактор тарифов. Текст «Границы задаются на карте» не заменяет саму карту.
- Не менять при сохранении суммы действующих вариантов и не обнулять отсутствующие в HTML поля.

### 6.2. Отдельное изменение правил: целевая модель

Цель: зона определяет допустимость адреса и базовый тариф по сумме товаров; вариант определяет дату, интервал и режим «как можно скорее». Если продукту нужна платная срочность, у варианта есть явно названная надбавка. Самовывоз — 0 ₽. Геопроверка и правило «вне зон» действуют и при выбранном варианте. Клиент получает предварительную цену; сервер самостоятельно проверяет адрес, вариант, товары, бонусы и итог перед созданием заказа.

До миграции прочитать действующие `DeliveryOption`, зоны и тарифы **каждого** tenant-а на копии БД. Общую зону без полигона можно создать автоматически только если она однозначно описывает прежнюю цену. Если цены или пороги у вариантов отличаются и не укладываются в новую формулу, сохранить старый режим для данного ресторана и потребовать явной настройки; не угадывать преобразование. На время поэтапного перехода ввести внутреннюю версию расчёта для tenant-а: отсутствие поля в старой записи означает `legacy-option`, новая схема включается только после проверки и явного переключения на `zone-v2`. В парсере старых данных значение по умолчанию должно быть `legacy-option`; в новом seed нужно записывать `zone-v2` явно. После переноса всех ресторанов удалить старую ветку. Исторические `Order.itemsTotal`, `deliveryPrice`, `total`, `deliveryOptionName` остаются снимками и не пересчитываются.

Разделить серверную проверку адреса (`resolveGeoDelivery`) и чистый расчёт тарифа. Целевой тариф: `стоимость зоны по порогу суммы товаров + надбавка варианта`, самовывоз — 0 ₽. Надбавка — целое неотрицательное число, по умолчанию 0; если она равна нулю, отдельное поле в форме не нужно. Одним правилом пользоваться в `api/order/route.ts`, `lib/admin-order-edit.ts`, `api/delivery/zone/route.ts`, `api/delivery/slots/route.ts` и `components/cart/cart-sheet.tsx`; предварительная сумма клиента не является доверенной. Проверить недоступную и выключенную зону, адрес вне зон, отсутствие геокодера, вариант с закрытым днём, заказ ниже минимума, бонусы и бесплатный порог. Для денег и заказов сначала написать падающие тесты.

## 7. Остальные решения по макету

### WhatsApp и каналы связи

Контактный WhatsApp находится в `restaurant.socials.whatsapp`, кнопка после заказа сейчас использует `settings.channels.whatsapp.phone`, а ссылки ответа сотрудника зависят от `settings.guestContact`. Это три разных назначения. При первом подключении показывать действующие значения без сброса. Для значения «номер из контактов» вычислять эффективный номер на сервере; отдельный номер хранить как явное переопределение. Если существующий номер заказов отличается от публичного, сохранить его. Пустой номер заказа не должен включать кнопку с пустой ссылкой. Telegram/MAX/email уведомления о заказах не смешивать с ручной кнопкой WhatsApp.

### Звук

Добавить `none` в тип, разбор и API сохранения `adminSound`, а в `AdminNotifications` не запускать проигрывание при этом значении. События и счётчики заказов/броней продолжают работать. Переключение на `none` не удаляет загруженный пользовательский файл. Диапазон повторов в рабочей форме — 1–20, как на сервере, а не 1–10 из HTML. Отдельное включение звука в конкретной вкладке браузера нужно для разрешения воспроизведения и остаётся локальным действием сотрудника.

### Сайт и контент

Для страниц, фото, акций, залов и печати использовать текущие данные БД. В редакторе печати оставить настройки цвета/логотипа/телефона/адреса, настоящий QR, загрузку PDF/PNG/SVG и принудительный canonical URL. В галерее и залах оставить удаление фото. В акциях сохранить действующие даты и добавить отдельный `enabled`, не заменяя им расписание: обновить `prisma/schema.prisma`, серверную выборку, действия, seed и `promosSchema` в `content-schema.ts`; старые акции после миграции остаются включёнными. В «Сотрудниках» нельзя ограничиться формой добавления: нужны редактирование существующих записей и отзыв доступа. В «Подписке» показывать ответ платформы, а не статичную фразу из HTML.

## 8. Порядок выполнения и проверки

1. **Зафиксировать исходное состояние.** Проверить `git status`, не затронуть `test-front/app`, не подмешать демонстрационные данные. Выписать действующие ключи настроек и варианты доставки на копии tenant-БД. Изменения другого исполнителя не сбрасывать.
2. **Устранить подтверждённые расхождения хранения и прав.** Адресное сохранение JSON, типизированное `banquets`, проверка `manage` при загрузке владельческих файлов. Тестами доказать, что сохранение одной секции не меняет другую.
3. **Сделать внутренние маршруты и оболочку.** Начать с 360 px, затем проверить широкий экран. Сохранить защищённые старые URL. Подключать страницы по одной, используя реальные источники и действующие операции.
4. **Подключить специфичные действия.** Прайсинг с транзакционным пересчётом; часы с часовым поясом; реальные загрузки; звук `none`; WhatsApp с сохранением разных номеров; CRUD и экспорт. После каждого блока сверять данные после перезагрузки.
5. **Провести приёмку первого выпуска.** Unit/integration для сохранения и прав, E2E для владельца и сотрудника с/без PIN, мобильные 360/390/768 px и desktop, проверка реальных данных двух разных tenant-ов. Результат не должен менять суммы существующих заказов или расчёт новых.
6. **Отдельно мигрировать доставку.** Сначала падающие тесты для денежных сценариев, затем единый расчёт и совместимость со старым режимом, проверка на копиях БД и поэтапное переключение ресторанов.

Минимальный набор регрессионных проверок: сохранение контактов не меняет расписание, галерею и `sync`; изменение зон не сбрасывает платёжные настройки и банкеты; неудачный пересчёт цен откатывает настройку; сотрудник без PIN не получает владельческие данные, с PIN может загрузить логотип; меню работает без PIN; «Без звука» не отключает счётчики; старый отдельный номер WhatsApp остаётся; акции с истёкшей датой скрыты; печатный QR ведёт на canonical; чужие данные не появляются у другого ресторана; корзина, API заказа и редактирование заказа показывают одинаковую сумму при каждом режиме доставки.

## 9. Критерии готовности

- Все 17 экранов макета представлены внутри «Настроек». Для каждого показанного поля есть серверное чтение и сохранение либо обоснованное исключение по этому документу.
- В главной навигации нет акций, доставки, сотрудников и других владельческих настроек как рабочих разделов сотрудника.
- В интерфейсе нет повторяющихся заголовков и подсказок, которые пересказывают подпись поля. Состояния «не сохранено», «сохраняется», «сохранено», ошибка различимы и соответствуют результату сервера.
- Сохранение одной секции не стирает другие поля JSON, включая неизвестные форме значения и `banquets`; одновременные изменения одной секции не затирают друг друга молча.
- Действующие возможности карты, фото залов, экспорта, команды, подписки и синхронизации сохранены.
- Права проверяются на странице, в действиях и API; изоляция tenant-ов, пути медиафайлов и секреты соблюдены.
- На 360 px нет горизонтальной прокрутки, все зоны касания не меньше 44 px, формы доступны с клавиатуры; старые прямые ссылки на владельческие страницы работают или защищённо перенаправляются.
- Тесты денег и заказов созданы до изменения расчёта и проходят вместе с действующими тестами проекта. `docs/PLAN.md`, `docs/ARCHITECTURE.md` и при изменении схемы `docs/CONTENT-SCHEMA.md` соответствуют коду.

Не считать первый выпуск завершением второго: в нём ещё действует прежняя цена варианта доставки. Статус этапов записывать в `docs/PLAN.md` только по реально выполненным изменениям.
