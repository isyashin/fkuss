# Редизайн админки

**Статус:** комплект макетов и задание на внедрение подготовлены; рабочая админка по ним ещё не переделана. Начать с [HANDOFF.md](HANDOFF.md).

## Что находится в папке

- [settings-redesign-preview.html](settings-redesign-preview.html) — автономный макет 17 экранов владельческих настроек. Пункты главной навигации открывают второй файл из этой папки.
- [staff-redesign-preview.html](staff-redesign-preview.html) — автономный макет заказов, броней и меню. Прямые ссылки на экраны: [заказы](staff-redesign-preview.html#orders), [брони](staff-redesign-preview.html#bookings), [меню](staff-redesign-preview.html#menu).
- [HANDOFF.md](HANDOFF.md) — порядок внедрения всего дизайна, источники истины, сохранение действующих функций и решения в местах, где HTML упрощает работу приложения.
- [DESIGN-SPEC.md](DESIGN-SPEC.md) — визуальная система, адаптивность и единые правила взаимодействия.
- [CJM-ACCEPTANCE.md](CJM-ACCEPTANCE.md) — маршруты пользователя и обязательные проверки готового приложения.
- [IMPLEMENTATION.md](IMPLEMENTATION.md) — подробная карта текущего кода, данных и прав для раздела «Настройки».
- [STAFF-DESIGN.md](STAFF-DESIGN.md) — решения и серверные ограничения для заказов, броней и меню.

Оба HTML-файла можно открыть локально без сборки и интернета. Переход между ними перезагружает страницу: демонстрационные правки при этом пропадают. Макеты показывают композицию и основные взаимодействия, но не реализуют серверные действия. Примерные названия, телефоны, цены и фотографии из HTML нельзя переносить в рабочий код. Реальные данные брать из БД текущего ресторана и его `CONTENT_DIR`.

Исходный `docs/settings-redesign-preview.html` остаётся отдельно. Копия в этой папке дополнена ссылками на макет сотрудника, поэтому файлы больше не побайтно одинаковы.

## Граница макета «Настройки»

В главной навигации остаются четыре пункта: **Заказы, Брони, Меню, Настройки**. Заказы и брони обслуживает сотрудник. Меню сотрудник может редактировать. Все остальные владельческие действия находятся **внутри «Настроек»**. Разные URL внутри `/admin/settings/…` допустимы: для пользователя это один раздел с общей внутренней навигацией.

Внутренняя навигация макета:

| Группа | Экраны |
|---|---|
| Ресторан | Данные и контакты; Часы работы |
| Сайт | Оформление; Страницы; Фотографии; Акции; Банкеты; Печатные материалы |
| Заказы и брони | Доставка и самовывоз; Оплата и бонусы; Бронирование |
| Меню | Правила цен; Импорт из Яндекс.Еды |
| Связь | Связь с гостем; Уведомления |
| Доступ и подписка | Сотрудники; Подписка |

Название группы не повторяется заголовком внутри каждого редактора. Подпись поля должна объяснять само поле; вводный текст оставлять только там, где он сообщает правило или последствие действия. Не добавлять декоративные статусы, карточки вокруг каждой строки и повторяющиеся кнопки сохранения.

## Визуальное поведение

- На широком экране: тёмная узкая главная навигация, светлая панель разделов настроек, один рабочий редактор. Сохранить сдержанную типографику, ровные линии, спокойный фон и один акцентный цвет макета. Фото и реальные данные важнее украшений.
- На телефоне: верхняя строка, один список выбора раздела, рабочий редактор и нижняя навигация. Верстать и проверять начиная с 360 px. Касаемые зоны — не меньше 44 px.
- На экране открыта только выбранная задача. Переход между задачами не должен требовать прокрутки мимо остальных настроек.
- Кнопка «Сохранить» относится только к видимому редактору и появляется после изменения. При переходе с несохранёнными правками нужно предложить остаться или уйти. После ошибки введённое остаётся на экране; «Сохранено» показывается только после подтверждения сервера.
- Загрузка файла, удаление записи, синхронизация, скачивание макета и пополнение баланса — отдельные действия. Для них не создавать фиктивную общую кнопку «Сохранить».
- Тема **сайта** и личная тема **панели администратора** — разные настройки. Выбор темы панели не должен менять витрину ресторана.
- На сервере и в интерфейсе проверять доступность зависимых полей: выключенное бронирование, недоступный вариант доставки, отключённый канал, отсутствие карты или ключа геокодера.

## Утверждённые смысловые решения

1. Макет задаёт расположение и язык экранов. Схемы БД, серверные проверки и уже сохранённые значения имеют приоритет при подключении.
2. Никакая настройка, скрытая в новом интерфейсе, не сбрасывается при сохранении соседнего раздела.
3. Действующие операции — редактирование зон на карте, фотографий залов, сотрудников, экспорт печати и счета — сохраняются внутри «Настроек», даже если в HTML показана только их краткая форма.
4. Изменение правила стоимости доставки выполняется отдельным этапом после безопасного переноса интерфейса. Целевая схема описана в `IMPLEMENTATION.md`; старые цены нельзя молча интерпретировать как цены зон.
5. Сигнал «Без звука» и переключатель видимости акции из макета нельзя считать готовыми функциями: способ их реализации определён в `IMPLEMENTATION.md`.

## Правила проекта для исполнителя

Перед изменением кода прочитать корневой `AGENTS.md`, `template/AGENTS.md`, относящиеся к задаче части `docs/PLAN.md` и `docs/ARCHITECTURE.md`. Папку `test-front/app` сохранить на исходном месте. Новые поля и решения отражать в `docs/PLAN.md`, а схему контента — в `docs/CONTENT-SCHEMA.md`. Для денежных правил сначала написать падающие тесты. Не включать в репозиторий ключи, токены или данные конкретного ресторана.
